# GTX 1080 (Pascal, sm_61, 8 GB) vs RTX 3090 (Ampere, sm_86, 24 GB) for Qwen3-0.6B finetuning

Researched 2026-08-31. Every claim below has a source URL and a literal quote.

## Verdict

**Yes, a GTX 1080 can still finetune Qwen3-0.6B in 2026 — but only on a narrow, explicitly
pinned path.** You must install the `cu126` PyTorch wheel, train in `fp32` or `fp16`
(never `bf16`), use PyTorch SDPA (never flash-attn), and skip Unsloth and Triton
entirely. LoRA/QLoRA fits comfortably; full fp32 finetune with Adam does not fit in 8 GB.

Working command surface:

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu126
```

```python
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-0.6B",
    dtype=torch.float32,              # NOT "auto" -- Qwen3 configs are bf16
    attn_implementation="sdpa",       # NOT "flash_attention_2"
)
SFTConfig(
    fp16=True, bf16=False,            # bf16 is emulated garbage on Pascal
    optim="adamw_bnb_8bit",           # bnb 8-bit optim: CC 6.0+, OK
    gradient_checkpointing=True,
    packing=False, padding_free=False,# both need FlashAttention-2
    torch_compile=False,              # inductor needs Triton (CC 8.0+)
)
```

## 1. CUDA 13.0 dropped Maxwell / Pascal / Volta

**Yes.** CUDA 13.0 removed offline compilation and library support for these architectures.

> "Architecture support for Maxwell, Pascal, and Volta is considered feature-complete. Offline
> compilation and library support for these architectures have been removed in CUDA Toolkit 13.0
> major version release. The use of CUDA Toolkits through the 12.x series to build applications for
> these architectures will continue to be supported, but newer toolkits will be unable to target
> these architectures."
>
> — CUDA Toolkit 13.0 Release Notes, §2.6.2 "Deprecated Architectures",
> https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html

The math libraries say the same in their own words:

> "Removed support for Maxwell, Pascal, and Volta GPUs, corresponding to compute capabilities
> earlier than Turing." — cuFFT: Release 13.0, same page
>
> "Dropped support for pre-Turing architectures (Maxwell, Volta, and Pascal)." — cuSPARSE: Release 13.0, same page

The warning was given one release earlier:

> "Maxwell, Pascal, and Volta architectures are now feature-complete with no further enhancements
> planned. While CUDA Toolkit 12.x series will continue to support building applications for these
> architectures, offline compilation and library support will be removed in the next major CUDA
> Toolkit version release."
>
> — CUDA Toolkit 12.9 Release Notes, §1.5.2,
> https://docs.nvidia.com/cuda/archive/12.9.0/cuda-toolkit-release-notes/index.html

### Newest toolkit that still supports sm_61

**CUDA 12.9** (the last 12.x release). Anything 13.x cannot target sm_61.

### Which PyTorch wheel index a GTX 1080 user must install

**`https://download.pytorch.org/whl/cu126`.** This is the only CUDA build PyTorch still ships that
contains Pascal-compatible SASS. The build matrix on `main` is explicit:

```python
TORCH_CUDA_ARCH_LIST_TABLE: dict[str, dict[str, set[int]]] = {
    "12.6": {"x86_64": {50, 60, 70, 75, 80, 86, 90}, "aarch64": {80, 90}},
    "13.0": {"x86_64": {75, 80, 86, 90, 100, 120}, ...},
    "13.2": {"x86_64": {75, 80, 86, 90, 100, 120}, ...},
    "13.4": {"x86_64": {75, 80, 86, 90, 100, 120}, ...},
}
```

— https://raw.githubusercontent.com/pytorch/pytorch/main/.ci/manywheel/build_env_setup.py

Note `61` is not in that set, but `60` is, and PyTorch's own compatibility table says an sm_60
cubin runs on a 6.1 device:

```python
DEVICE_REQUIREMENT: dict[int, _CompatSet | _CompatInterval] = {
    ...
    60: _CompatInterval(start=60, exclude={62}),
```

— https://raw.githubusercontent.com/pytorch/pytorch/main/torch/cuda/__init__.py

So a GTX 1080 (CC 6.1) executes the sm_60 kernels in the cu126 wheel. It executes nothing in a
cu128 / cu13x wheel; PyTorch prints "Found GPU0 ... which is of compute capability (CC) 6.1 ...
Your installed torch==... does not include kernels for this GPU."

CUDA 12.6 is still an actively built PyTorch target on `main` (`CUDA_ARCHES = ["12.6", "13.0",
"13.2", "13.4"]`, same file), and `cu126` wheels are published through torch 2.13.0 on
https://download.pytorch.org/whl/cu126/torch/ — verified by listing that index.

The deliberate decision to keep 12.6 as the Pascal escape hatch is recorded here:

> "For Release 2.8 Option 1 (Currently in trunk):
>  CUDA 12.6: 5.0;6.0;7.0;7.5;8.0;8.6;9.0
>  CUDA 12.8: 7.5;8.0;8.6;9.0;10.0;12.0 -> Version Released on pypi"
>
> — pytorch/pytorch issue #157517, "[release 2.8-2.9] Delete support for Maxwell, Pascal, and Volta
> architectures for CUDA 12.8 and 12.9 builds", https://github.com/pytorch/pytorch/issues/157517

**Consequence:** the default `pip install torch` from PyPI (which tracks the current stable CUDA,
`CUDA_STABLE = "13.0"`) gives a 1080 user a torch that cannot run a single kernel. The `--index-url`
is mandatory, not optional.

## 2. FP16 throughput of GP104: 1:64 confirmed

**The 1:64 figure is correct.** NVIDIA's own instruction throughput table:

> Table 7. Throughput of Native Arithmetic Instructions (Number of Results per Clock Cycle per
> Multiprocessor). Compute Capability **6.1**:
> 16-bit floating-point add, multiply, multiply-add = **2**
> 32-bit floating-point add, multiply, multiply-add = **128**
>
> — CUDA C++ Programming Guide 12.9, §6.4.1 Arithmetic Instructions,
> https://docs.nvidia.com/cuda/archive/12.9.0/cuda-c-programming-guide/index.html

2 / 128 = **1/64**. Note CC 6.0 (GP100, Tesla P100) has 128 — the crippling is specific to the
consumer GP104/GP102 dies, i.e. exactly the GTX 1080.

Absolute numbers agree:

> GeForce GTX 1080, GP104-400-A1: Single precision (boost) **8228 (8873)** GFLOPS,
> Double precision (boost) 257 (277), Half precision (boost) **128 (139)**
>
> — https://en.wikipedia.org/wiki/GeForce_10_series

8873 / 138.6 = 64.0. On this card FP16 is slower than FP64.

### Is `fp16=True` a speedup or a slowdown?

**Neither dramatic. It is roughly neutral, usually a modest net win, and it is *not* 64x slower.**

The 1:64 rate applies to *native FP16 ALU instructions*. PyTorch AMP does not run GEMMs through
those: cuBLAS on a non-Tensor-Core GPU executes half-precision GEMM with an FP32 compute type, at
the FP32 rate, so the matmuls cost about the same as FP32 while the tensors take half the memory
and half the bandwidth. PyTorch states the outcome directly:

> "Mixed precision primarily benefits Tensor Core-enabled architectures (Volta, Turing, Ampere).
> This recipe should show significant (2-3X) speedup on those architectures. **On earlier
> architectures (Kepler, Maxwell, Pascal), you may observe a modest speedup.**"
>
> — PyTorch Automatic Mixed Precision recipe,
> https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html

So: keep `fp16=True` on a 1080 for the memory saving (it is what makes an 8 GB card viable), expect
0-30% speed change, not 2-3x. If you hit numerical instability, fall back to pure fp32 — you lose
little speed on this card.

**Caveat to watch:** any *hand-written* fp16 elementwise kernel, or any library that does real
half-precision arithmetic rather than fp32-accumulate GEMM, will hit the 1/64 rate. That is a real
risk for third-party fused kernels, not for stock `torch.autocast`.

### Does Pascal support bf16?

**No hardware support.** PyTorch's own definition of native support is compute capability >= 8:

```python
def is_bf16_supported(including_emulation: bool = True):
    ...
    if torch.cuda.get_device_properties(device).major >= 8:
        return True
    if not including_emulation:
        return False
    # Finally try to create a bfloat16 device.
    return _check_bf16_tensor_supported(device)
```

— https://raw.githubusercontent.com/pytorch/pytorch/main/torch/cuda/__init__.py

Flash-attention states the same hardware fact independently:

> "Datatype fp16 and bf16 (bf16 requires Ampere, Ada, or Hopper GPUs)."
>
> — https://github.com/Dao-AILab/flash-attention/blob/main/README.md

**Trap:** `including_emulation` defaults to `True`, and allocating a bf16 tensor on a 1080 succeeds,
so `torch.cuda.is_bf16_supported()` returns **True** on a GTX 1080. Transformers checks exactly
that function (see §6), so `bf16=True` may be *accepted* and then run emulated. Verify on the real
box with:

```bash
python -c "import torch; print(torch.cuda.is_bf16_supported(including_emulation=False))"  # expect False
```

## 3. Unsloth: documented minimum is CC 7.0

> "Supports NVIDIA GPUs since 2018+ including Blackwell RTX 50 and DGX Spark.
> **Minimum CUDA Capability 7.0** (V100, T4, Titan V, RTX 20 & 50, A100, H100, L40 etc)
> Check your GPU! **GTX 1070, 1080 works, but is slow.**
> ... Your device should have `xformers`, `torch`, `BitsandBytes` and `triton` support."
>
> — https://docs.unsloth.ai/get-started/beginner-start-here/unsloth-requirements

So the docs both set the floor at 7.0 and claim 1070/1080 "works, but is slow". There is no hard
compute-capability refusal in `unsloth/__init__.py` (verified: no arch gate raises there), so import
will not fail up front.

**But treat this as effectively unsupported**, because of the last sentence in that quote: Unsloth's
speedups are Triton kernels, and Triton's stated hardware floor is CC 8.0:

> "Supported Hardware:
> - **NVIDIA GPUs (Compute Capability 8.0+)**"
>
> — https://github.com/triton-lang/triton/blob/main/README.md

Unsloth's own code also disables its Ampere-gated paths on Pascal:

```python
_FLEX_ATTENTION_MIN_CAPABILITY = (8, 0)
...
if major_version >= 8:
    SUPPORTS_BFLOAT16 = True
```

— https://raw.githubusercontent.com/unslothai/unsloth/main/unsloth/models/_utils.py

**Practical answer: do not use Unsloth on a GTX 1080.** Use plain `peft` + `transformers` + `trl`.

## 4. bitsandbytes minimum compute capability

The library floor is 6.0, and the per-feature table is explicit:

> "`bitsandbytes` is currently supported on NVIDIA GPUs with **Compute Capability 6.0+**. The library
> can be built using CUDA Toolkit versions as old as 11.8."
>
> | Feature | CC Required | Example Hardware Requirement |
> |---|---|---|
> | LLM.int8() | **7.5+** | Turing (RTX 20 series, T4) or newer GPUs |
> | 8-bit optimizers/quantization | **6.0+** | Pascal (GTX 10X0 series, P100) or newer GPUs |
> | NF4/FP4 quantization | **6.0+** | Pascal (GTX 10X0 series, P100) or newer GPUs |
>
> — https://huggingface.co/docs/bitsandbytes/main/en/installation

On sm_61 (GTX 1080):

| Feature | Works on sm_61? |
|---|---|
| (a) 8-bit optimizers (`AdamW8bit`, `optim="adamw_bnb_8bit"`) | **Yes** (CC 6.0+, Pascal named explicitly) |
| (b) 4-bit NF4 / QLoRA (`load_in_4bit=True`) | **Yes** (CC 6.0+, Pascal named explicitly) |
| (c) LLM.int8() (`load_in_8bit=True`) | **No** (needs CC 7.5+, Turing) |

One packaging caveat from the same page — the shipped binaries only contain `sm60` in the older
toolkit builds:

> | Linux x86-64 | 11.8 - 12.6 | GCC 11.2 | **sm60**, sm70, sm75, sm80, sm86, sm89, sm90 |
> | Linux x86-64 | 12.8 | GCC 11.2 | sm70, sm75, sm80, sm86, sm89, sm90, sm100, sm120 |
> | Linux x86-64 | 13.0 - 13.2 | GCC 11.2 | sm75, sm80, sm86, sm89, sm90, sm100, sm120 |

This lines up with §1: staying on `cu126` keeps you inside the only bitsandbytes variant that has
Pascal code. A cu128/cu13x torch would pick a bitsandbytes library with no sm60 cubin.

## 5. flash-attn: Ampere and newer only

> "FlashAttention-2 with CUDA currently supports:
> 1. **Ampere, Ada, or Hopper GPUs** (e.g., A100, RTX 3090, RTX 4090, H100). For Turing GPUs (T4,
> RTX 2080), see the separate flash-attention-turing repo, which supports a core subset of
> FlashAttention features on Turing.
> 2. Datatype fp16 and bf16 (bf16 requires Ampere, Ada, or Hopper GPUs)."
>
> — https://github.com/Dao-AILab/flash-attention/blob/main/README.md

FlashAttention-3 is worse: "Requirements: H100 / H800 GPU, CUDA >= 12.3." FlashAttention-4 targets
Hopper and Blackwell. **Confirmed: nothing in the Dao-AILab repo runs on Pascal.**

### Fallback for Pascal: PyTorch SDPA memory-efficient backend

PyTorch's SDPA has three backends with different arch floors, from `sdp_utils.cpp`:

```cpp
bool check_flash_attention_hardware_support(...) {
  using sm80 = SMVersion<8, 0>;
  using sm121 = SMVersion<12, 1>;
  ...
  "Flash attention only supports gpu architectures in the range [sm80, sm121]..."
}

bool check_mem_efficient_hardware_support(...) {
  // Mem Efficient attention supports hardware in the range [sm_50, sm_90]
  using sm50 = SMVersion<5, 0>;
  using sm121 = SMVersion<12, 1>;
  ...
  "Mem Efficient Attention only supports gpu architectures in the range [sm50, sm121]..."
}
```

— https://raw.githubusercontent.com/pytorch/pytorch/main/aten/src/ATen/native/transformers/cuda/sdp_utils.cpp

**sm_61 is inside `[sm50, sm121]`**, so the memory-efficient (cutlass, xformers-derived) kernel is
available on a GTX 1080, and the flash kernel is not. Set
`attn_implementation="sdpa"` and PyTorch dispatches to mem-efficient automatically; the math
backend is the always-available last resort. `xformers`' `memory_efficient_attention` is the same
lineage and also works, but is redundant now that it is upstreamed into SDPA.

## 6. TRL / transformers SFTTrainer: other Pascal blockers

Nothing is a hard blocker beyond §1-§5, but four things will bite:

**a) `bf16=True` raises — sometimes.** The guard is:

```python
if self.bf16 or self.bf16_full_eval:
    if not self.use_cpu and not is_torch_bf16_gpu_available() and not is_torch_xla_available():
        error_message = "Your setup doesn't support bf16/gpu. You need to assign use_cpu if you want to train the model on CPU."
        if is_torch_cuda_available():
            error_message += " You need Ampere+ GPU with cuda>=11.0."
        raise ValueError(error_message)
```

— https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/training_args.py

and `is_torch_bf16_gpu_available()` is just `return torch.cuda.is_bf16_supported()`
(https://raw.githubusercontent.com/huggingface/transformers/main/src/transformers/utils/import_utils.py),
which defaults to `including_emulation=True` (see §2). So on a 1080 this check can **pass** and let
emulated bf16 through instead of raising. Set `bf16=False` yourself; do not rely on the guard.

**b) `dtype="auto"` picks bf16.** Qwen3 checkpoints are published in bfloat16, so `"auto"` loads
bf16 weights onto a card with no bf16 hardware. Pass `dtype=torch.float32` (or `torch.float16`)
explicitly.

**c) `packing=True` / `padding_free=True` silently require FlashAttention.**

> "padding_free ... Whether to perform forward passes without padding by flattening all sequences in
> the batch into a single continuous sequence. ... **Currently, this is only supported with the
> FlashAttention 2 or 3**, which can efficiently handle the flattened batch structure. **When packing
> is enabled with strategy `'bfd'`, padding-free is enabled, regardless of the value of this
> parameter.**"
>
> — https://raw.githubusercontent.com/huggingface/trl/main/trl/trainer/sft_config.py

So `packing=True` transitively demands flash-attn. Keep both off on Pascal.

**d) `torch_compile=True` will not work.** Inductor's GPU backend generates Triton, and Triton
requires CC 8.0+ (§3). Also `tf32=True` raises "--tf32 requires Ampere or a newer GPU arch, cuda>=11
and torch>=1.7" (`training_args.py`, same file) — TF32 is an Ampere feature.

The core `Trainer` fp16 path (`torch.autocast` + `GradScaler`), gradient checkpointing, `peft` LoRA,
and `adamw_torch` / `adamw_torch_fused` / `adamw_bnb_8bit` have no architecture gate.

## Memory arithmetic for Qwen3-0.6B on 8 GB

Qwen3-0.6B is ~0.6 x 10^9 parameters.

| Recipe | Weights | Grads | Adam states | Total (excl. activations) | Fits 8 GB? |
|---|---|---|---|---|---|
| Full FT, fp32, AdamW | 2.4 GB | 2.4 GB | 4.8 GB | **9.6 GB** | No |
| Full FT, fp16 AMP, AdamW | 2.4 GB (fp32 master) | 2.4 GB | 4.8 GB | **9.6 GB** | No (AMP does not shrink optimizer state) |
| Full FT, fp16 AMP, `adamw_bnb_8bit` | 2.4 GB | 2.4 GB | 1.2 GB | **6.0 GB** | Tight — needs bs=1, short seq, gradient checkpointing |
| LoRA r=16, fp16 AMP | 1.2 GB (fp16 frozen) | ~0 | ~0.02 GB | **~1.3 GB** | Yes, easily |
| QLoRA NF4 | ~0.4 GB | ~0 | ~0.02 GB | **~0.5 GB** | Yes (but NF4 dequant cost is not worth it at 0.6B on 8 GB) |

**Recommended on a 1080: LoRA (not QLoRA) + fp16 + SDPA.** 8 GB is plenty for a 0.6B LoRA, so the
4-bit quantization overhead buys nothing.

## Side-by-side

| | GTX 1080 (sm_61, 8 GB) | RTX 3090 (sm_86, 24 GB) |
|---|---|---|
| Newest CUDA toolkit | **12.9** | current (13.4) |
| PyTorch wheel index | **`cu126` only** | any (`cu126`/`cu128`/`cu130`/`cu132`) |
| Default `pip install torch` | **broken** (no sm_6x kernels) | works |
| FP32 | 8.9 TFLOPS | ~35.6 TFLOPS |
| FP16 | 0.139 TFLOPS (1:64) | ~35.6 TFLOPS dense / ~71 TFLOPS tensor-core |
| bf16 | **none** (emulated only) | native |
| TF32 | no | yes |
| flash-attn | **no** | yes |
| PyTorch SDPA mem-efficient | yes (`[sm50, sm121]`) | yes |
| Triton / `torch.compile` GPU | **no** (needs CC 8.0+) | yes |
| Unsloth | nominally "works, but is slow"; **avoid** | fully supported |
| bnb 8-bit optimizers | yes | yes |
| bnb NF4 / QLoRA | yes | yes |
| bnb LLM.int8() | **no** (needs 7.5+) | yes |
| Qwen3-0.6B full finetune | only with 8-bit optimizer, very tight | trivially |
| Qwen3-0.6B LoRA | yes | yes, ~10-20x faster |

**Bottom line:** the 1080 is a *working* but *dead-end* card for this. It will train
Qwen3-0.6B LoRA correctly today on `cu126`, and that path gets no new CUDA toolkit, no Triton, no
flash-attn, and no bf16 ever. The 3090 is not merely faster — it is the first architecture where
the modern finetuning stack is fully available.
